# Internal event lifecycle command

Этот контракт предназначен для планировщика отдельного `notify_service`. Монолит остаётся единственным владельцем мероприятий, их статусов и допустимых переходов.

## Endpoint и аутентификация

`POST /internal/v1/events/{eventId}/lifecycle/advance`

Тело запроса отсутствует. В частности, вызывающий сервис не передаёт целевой статус или текущее время.

Обязательный заголовок:

```http
X-Internal-Token: <service-token>
```

Монолит читает токен из `NOTIFY_SERVICE_TOKEN`. Пустая конфигурация отклоняется при проверке конфигурации, поэтому сервер в штатном режиме с ней не запускается. Middleware дополнительно работает fail-closed и отклоняет все вызовы, если его всё же создали с пустым токеном. Отсутствующий или неверный токен возвращает `401` с общим error DTO. Пользовательский JWT не заменяет внутренний токен. Значение токена нельзя включать в логи.

## Успешный ответ

Любой успешно обработанный запрос, включая запрос, для которого переход ещё не нужен или уже был применён, возвращает `200`:

```json
{
  "eventId": 123,
  "previousStatus": "Набор",
  "currentStatus": "В процессе",
  "outcome": "started",
  "applied": true,
  "startTime": "2026-08-15T10:00:00Z",
  "endTime": "2026-08-15T12:00:00Z",
  "processedAt": "2026-08-15T10:00:00Z"
}
```

`processedAt` определяется серверными часами монолита. `previousStatus` означает состояние, прочитанное внутри текущей транзакции после получения блокировки строки.

## Outcomes

| outcome | applied | Значение |
| --- | ---: | --- |
| `not_due` | `false` | Мероприятие находится в `Набор`, но `start_time` ещё не наступил. |
| `started` | `true` | `Набор` переведён в `В процессе` в момент `start_time` или после него, но до `end_time`. |
| `completed` | `true` | `В процессе` переведён в `Завершена` в момент `end_time` или после него. |
| `completed_catch_up` | `true` | После простоя `Набор` сразу переведён в `Завершена`, потому что `end_time` уже наступил. |
| `already_active` | `false` | Актуальное состояние уже `В процессе`, а `end_time` ещё не наступил. |
| `already_completed` | `false` | Актуальное состояние уже `Завершена`. |

В catch-up-сценарии переход через `В процессе` не выполняется и запоздалое событие `event.started` не должно создаваться.

## Ошибки

Ошибки используют общий DTO проекта с полями `error` и `message`:

- `400 invalid_event_id` — `eventId` отсутствует, равен нулю или имеет неверный формат;
- `401 invalid_internal_token` — внутренний токен отсутствует, неверен или не настроен;
- `404 event_not_found` — мероприятие не существует;
- `409 invalid_event_lifecycle_state` — статус неизвестен, обязательная запись целевого статуса отсутствует либо временной интервал мероприятия некорректен;
- `500 event_lifecycle_failed` — ошибка инфраструктуры или транзакции.

При ошибке транзакция откатывается, частичное изменение статуса не сохраняется.

## Повторы, конкуренция и идемпотентность

Команду можно повторять после сетевой ошибки или неопределённого ответа. Каждый вызов читает актуальное состояние внутри транзакции с блокировкой строки мероприятия (`FOR UPDATE` в PostgreSQL), сам вычисляет допустимый переход и возвращает итоговое состояние. Параллельные запросы не должны применять один переход дважды.

Команда не создаёт уведомлений, email, push-сообщений или inbox-записей, поэтому повтор lifecycle-вызова не создаёт delivery side effects. Отдельный transactional schedule outbox записывается только командами create/reschedule/delete мероприятия и описан в `event_lifecycle_schedule_outbox_contract.md`; сам lifecycle advance не публикует новую schedule-запись. Lifecycle-решение остаётся в application-сервисе монолита.

## Ожидаемое поведение notify_service

`notify_service` хранит собственные задания планировщика и с retry вызывает эту команду вблизи `start_time` и `end_time`. Он должен считать любой `200` успешной обработкой, учитывать `outcome` и безопасно повторять запрос при временных/сетевых ошибках. Для `completed_catch_up` он не отправляет уведомление о начале.

`notify_service` не имеет права напрямую читать или изменять таблицы мероприятий монолита и не импортирует Go-реализацию монолита. Интеграция выполняется только через явный версионированный внутренний контракт.

## Swagger

Внутренние маршруты не включены в публичную Swagger-схему `/swagger`: она описывает пользовательский API и Bearer-аутентификацию. Этот отдельный документ является контрактом service-to-service endpoint и предотвращает публикацию внутренней token-схемы как пользовательского API.
